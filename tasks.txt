NEW7: [NEW 2026-11-15] Autoplans on the server: reuse first, then the right model
Steps inside a concept (NEW13, see /dev/path) change what a new plan is written from:
- The writer gets one line per concept: the step the player is on, its state and newest rating, and the next step.
  This takes the place of part of the list of rated blocks.
- The shortlist (step 0, no AI) can ask the library for "the next step this player hasn't made solid", once blocks
  can be found by step. A whole plan fits when its exercises are at the player's steps or one above.
- A plan written by the AI sets a tool's `level` or stage for every concept that has a ladder, so its step can be read.
- A teacher's note (NEW12) skips the reuse step: that plan is always written by the AI.
From NEW8, before the server calls the library per player: the use totals are whole-table sums on every call (narrow
them to the candidate blocks); coverage with a player in scope also counts that player's private blocks; nothing writes
plan_reviews.library_plan_id yet, so library plans show no reviews; a plan's rows must name only blocks the app owns.
Builds on NEW8 (the query and the tools). Decided there: a fitting whole plan the player hasn't had is used whole;
otherwise the AI writes one, searching blocks through tools (unused blocks for new things, the blocks they had for the
same again); the examples leave the writer's prompt and the player's progress and used blocks go in; least-used blocks
first.
Use brainstorming first (the brainstorming skill), before any spec or code.
The flow:
0. Match the request against the seed library in our own code (no AI): a shortlist of library plans that fit the
   player's answers.
1. Assess with a cheap model: it can query only that shortlist, through a tool (MCP), and says whether one plan fits.
   The server sets what "matches" means; the model can't widen the search.
2. Decide, in the same call: if nothing fits, which writer a new plan needs (cheap writer, or a dearer one for hard plans).
3. Dispatch to that model to write the plan; store it in the library for the next player.
To settle in brainstorming:
- MCP server or plain tool definitions in the API request (MCP pays off if the dev tools and the browser's AI use the
  same query). Or no tool at all: shortlist summaries in the prompt, plus get_plan(id) only when a summary isn't enough.
- Each tool call is a round trip that sends the conversation again: cap the calls, and use prompt caching.
- Which models: the Assess / Write / Hard plans picks on /dev/costs (Other models on OpenRouter) are from price only.
  Check which support tool calling on OpenRouter, then run the shortlist on our prompts (npm run compare-models).
- The writer prompt is about 108k tokens, over Haiku 5.5's 100k line, so every plan costs 5x. Getting it under 100k
  (the library no longer in the prompt) cuts that without changing model.
- Keep new_plan_percent as the share written new, and record per autoplan what happened (reused, which model wrote it,
  tokens) so /dev/costs can use real numbers instead of PICK_TOKENS and the chance.
- Allowances, Batch (half price, results within the hour, up to 24 hours) and what the player sees while a plan is written.
Then: /dev/costs models assess as one request; add tool calls per assess once the design is set.
