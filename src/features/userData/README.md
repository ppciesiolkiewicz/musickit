# User data

A signed-in player's data on the server: a few documents (plan, note, course notes, creator key, records, about) and the progress log, one row each per player. This part holds the rules for reading and storing them, the routes, and the client that saves to them; the screens' use of it comes in later parts.

## Parts

- `model.ts`: pure, client-safe. `DOC_KINDS`, `DocKind`, `isDocKind`, `MAX_DOC_BYTES` (512 KB of JSON), `MAX_PLAN_BYTES` (2 MB: the running plan, up to 60 earlier ones and the given plans), `maxDocBytes(kind)`, and `parseDoc(kind, raw)`, which reads a document with its feature's own parser (`sanitiseState` for the plan, then `fitPlanState`, which drops the oldest earlier plans until it fits the cap, and with none left the oldest given plans, never the newest one, `parseBlock` for the note, `parseNotesStore`, `sanitiseKey`, and `readLevel`, `readOverrides` and `savedVoice` for about). `records` is `{ improv: { done, best }, noteGameBest, lipRollAccuracy }`: the counts fall back to 0, and `lipRollAccuracy` keeps only a value of `ROLL_ACCURACIES` (`exercises/basics/rollAccuracy.ts`), else null (the warm-up then uses Easy).
- `server/`: server only.
  - `repo.ts`: `UserDataRepo`, what the rules need from storage, including the `videos` rows (`VideoRow`; `createVideo`, `listVideos`, `getVideo`, `renameVideo`, `deleteVideo`, `canWatch`, used by `features/videos/server/access.ts`), the `shares` rows (`ShareRow`; `createShare`, `getShare`, `listShares`, `stopShare`, `claimPlan`) and `videoPaths` (the user's videos' blob paths, read before Delete account deletes the user row, which cascades every row of theirs; the files are deleted after; `repo.memory.ts` has `cascadeUser` to stand in for the cascade in tests). `canWatch` is one query: the owner, a live note share of the owner that lists the video, or a plan share of the owner that lists it and that this viewer claimed (stopped or not). The block library: `ownedBlockIds(userId, ids)` (which of the ids the user has a `block_owners` row for) and `addBlocks(userId, blocks, now)` (`NewBlock` with an optional `Provenance`, `BlockSource`: in one transaction the `blocks` rows not stored yet, then the owner rows, both `on conflict do nothing`, then provenance: a listed block whose `model`, `prompt_version`, `docs_agents` and `docs_teaching` are all null takes its own provenance, else its stored parent's; a block with any set is left; a null user is the app), `promoteExampleBlocks(ids)` (the app's owner rows of those blocks whose `source` is `example` become `seed`, enabled for reuse; any other row, a player's or a seed one turned off, is left; returns how many changed) and `setPlanBlocks(planId, rows)` (`PlanBlockRow`: replaces a plan's `practice_plan_blocks` rows in one transaction). The plan reviews: `syncPlanReviews(userId, planIds, rows)` (`PlanReviewRow`: makes the user's `plan_reviews` rows match; a row is added or changed only when its `at` differs, a row of a plan in `planIds` that has no row in `rows` is deleted, rows of plans not in `planIds` (dropped from the history) are left, no `planIds` does nothing) and `listPlanReviews(limit)` (every player's, newest first, for the review page). `putProgress` also writes `progress_entries.block_id`, `putPlanTime` `plan_day_times.blocks` and `on_dates` (`DayTime.on`, read back as `on`); a record sent without `blocks` or `on` keeps the stored ones, and an entry sent without a block id keeps the stored `block_id` and the `blockId` in its `entry` (`coalesce`; a slot's block never changes), so a tab still running code from before them doesn't wipe them. `repo.drizzle.ts` is Postgres (its `addBlocks`, `promoteExampleBlocks` and `setPlanBlocks` run on a local database in `npm run test:library-db`, see `features/library/README.md`), `repo.memory.ts` is for tests (its `peekBlocks`, `peekOwners` and `peekPlanBlocks` show the library).
  - `data.ts`: `readDoc`, `writeDoc` (checks the kind and the size against `maxDocBytes`, parses before storing; a plan save then fills the library with `storePlanBlocks` (the current plan, the history and the given plans), and a failure there is logged, never refuses the save: the next save repairs it), `reviewRowsOf` (one `plan_reviews` row for each plan, current, earlier or given, that has a `review`, one per plan id, the first kept, since two rows for one id would make the upsert throw; title from `config.title`, `libraryPlanId` null for now; a plan save then syncs them with `syncPlanReviews`, in its own try/catch, so a failure is logged, never refuses the save, and the next save repairs it) and `storePlanBlocks` (the parsed document's blocks the player doesn't own yet, ids worked out from `libraryBlocksOf` in `features/plan/model/libraryBlocks.ts`, `ai` or `edit`, never enabled for reuse; a parent is kept only when the player owns it or it is in the document; returns how many are new) and `putEntry` (one progress entry, replacing the exercise's earlier one), `readEntries` (the log, re-parsed on the way out).
  - `shares.ts`: sharing rules. `newShareId` (32 random bytes, base64url), `videoIdsIn(snapshot)` (every recording ref in the JSON), `shareNote` (a frozen copy of the stored note; `no-note` when it is empty), `sharePlan` (teachers and owners: `{ config }` of the plan named by id, the current plan or a given one, without the AI's `progress` notes; any other id, an earlier plan's too, is `not-found`), `shareNoteBlock` (a note given whole, the studio's stage, listed under the item `studio`; measured and parsed like a stored note, never stored as one), `openNoteShare` (a live note share or null), `readNoteShare` (what a reader gets: the note and `sharedAt`, never the owner), `liveLinks` (the owner's live links of one item, id and date only) and `claimInvite` (a copy of the invited plan, `from` the share id, first in the given plans, `PlanState.given`, whatever the current plan is; `current` and `history` are left as they are; a second claim returns the same copy, and puts it back if the document lost it). A share naming a recording that isn't one of the sharer's uploaded videos (a take still uploading, or someone else's) is refused with `video-not-uploaded` (the route's 409: "A video in this note is still uploading. Wait until it's up, then press Share.", shown in the popover), so every video in a share is in `share_videos`.
  - `seedBlocks.ts`: `libraryPlanBlocks(plans)` (the `practice_plans` plans' blocks as `SeedPlan`s `{ id, reply, provenance }`: `seed`, enabled, each with its plan's provenance, a block in two plans keeping the first's; a reply that doesn't parse is left out, named by `unparsedReplies`), `seedFileBlocks()` (the seed block files in `src/features/library/seed/blocks`, the former exercise examples among them: `seed`, enabled, each with its file's model and versions), `planBlockRows(reply)` (one `PlanBlockRow` per exercise slot, `day` and `place` from 0, `[]` when the reply doesn't parse) and `seedBlocks(repo, plans, now, files = SEED_BLOCKS)` (the seed files' blocks, then the plans' blocks in id order, so the first writer of a block sets both its provenance and its default slot: minutes, why and lessons; then `promoteExampleBlocks` on their ids, so a block an earlier run stored as an example's (`example`, not enabled) becomes `seed`, enabled; then `setPlanBlocks` for each plan, with no rows for a plan whose reply no longer parses; returns `{ library, planBlocks, promoted }`). Every config goes through `sanitiseState` first, so a seeded id is the id a player's plan of the same exercise gets. Owned by the app (`user_id` null). `npm run -s db:seed-blocks` (`scripts/db-seed-blocks.ts`) runs it over `practice_plans` at `DATABASE_URL`, printing the host first; blocks are insert-only and provenance is filled once, so a second run adds nothing and gives the same plan-block count.
  - `http.ts`: `userData()` (the repo, or null without a database) and `signedIn(req)` (the account, or the 503, 403 or 401 answer, or 409 `{ error: "account-changed" }` when the request's `X-Account-Id` names another account than the session's; a request without the header goes through, for curl and tests). The routes are `src/app/api/me/documents/[kind]`, `src/app/api/me/progress`, `src/app/api/me/plan/time` (the day timer's records, one `plan_day_times` row per plan and day, never the plan document: `GET ?plan=<id>` → `{ days }`, `GET` without `plan` → `{ days }` of every plan (`readAllPlanTimes`, `repo.listAllPlanTimes`: newest `updated_at` first, at most 1000; a `plan` over 200 characters is 400), `PUT { time }` replaces that day's, a broken one is 400; `readPlanTimes` / `writePlanTime` in `data.ts`) and `src/app/api/shares` (`POST { kind: "note", note? }` or `{ kind: "plan", planId }` (the own current plan or a given one: 403 `not-allowed` for a non-teacher, 400 without a `planId`, 404 `not-found` for any other id; the item is the plan's id), `GET ?kind=&item=` the owner's live links; `[id]`: a public `GET` of a live note link only (never a plan's snapshot), `DELETE` stops the owner's own, else 404; a share naming a video not uploaded yet is 409 `video-not-uploaded`; `[id]/claim`: `POST` claims a plan invite for the signed-in person, `{ planId }`, 410 stopped, 404 unknown); a changing method gets the Origin check, a GET only needs a session.
- `client/`: browser side, never imports `server/`.
  - `source.ts`: `DataSource` (`server`, `local`, `memory`) and `pickSource(accountsOn, signedIn)`: no accounts is `local`, signed in is `server`, a visitor is `memory`.
  - `useDataSource.tsx`: `useDataSource()` (`{ source, ready, accountId }` over `useAccount()` and `accountsOpen()`; `ready` waits for the account when accounts are on, and a session read that fails is asked again, not taken for a visitor (`features/account/serverAccountStore.ts`)) and `useSaveStatus()`, the worst status of every client with something unsaved.
  - `retry.ts`: `withRetry(send, { retryMs, schedule })`, a sender that reports a `SaveStatus` (`saved`, `saving`, `failed`, `rejected`, `signedOut`; DocClient adds `stale`) and retries. `run()` sends now; network errors and 5xx retry after `RETRY_MS` (2, 5, 15, 30 s, the last repeating); `failed` is only that retried case. A 401 is `signedOut` and any other 4xx (400, 403, 413) `rejected`, neither retried until `run()` again; `lastCode()` keeps the status code. `send` is called afresh each attempt. A one-off request (a progress entry) gets its own `withRetry`; DocClient builds on one.
  - `accountHeader.ts`: re-exports `accountHeaders(extra)`, `isAccountChanged` and `ACCOUNT_CHANGED_WORDS` from `features/account/serverAccountStore.ts`: the headers for a request that changes a player's data, with `X-Account-Id` (the account the page loaded for). Every app client that writes sends it: the documents, progress, the video routes and upload, the share routes, the claim, and `/api/account` (rename, delete). A tab still open under one account then can't write into another that logged in since: the 409 is `rejected`, never retried.
  - `docClient.ts`: `createDocClient({ put, version, onStale, delayMs = 1000, retryMs, schedule })`: each document has a version (`user_documents.version`, +1 on every write; GET answers `{ data, version }`). The client sends the version it loaded (`version`, or `setVersion(n)` for a store that makes the client before the load; it only goes up) and takes the new one from each answer; a save without a version still always lands. A 409 `stale` (changed on another device, or by a teacher) is status `stale`, not retried, calls `onStale` once (`reloadSoon`: the notice shows, then the page reloads) and sends nothing after it, so the reload loads the newer version. `save(value)` is sent a second after the last save, last write wins; `flush()` sends now, waits for a send already out, and returns the status (`saved` only once the latest value landed). `putDocument(kind)` is the real `put` (`PUT /api/me/documents/<kind>` with `{ data, version }`, `keepalive` when the body is under 64 KB).
  - `registry.ts`: the clients with something unsaved. `useSaveStatus` reads the worst (signedOut, then stale, rejected, failed, saving), `useSaveTooBig` whether a refusal was a 413, `useSaveAccountChanged` whether it was a 409 (another account logged in), and on `pagehide` every one is flushed with `keepalive`.
  - `load.ts`: `getJson(url)`, a read that waits `RETRY_MS` and asks again on network errors and 5xx (the page stays loading) and rejects a 4xx with `LoadRefused`. `loadReporter()`: the plan and note stores report a refused read through it, so the save notice shows "logged out" (401) or "rejected" (another 4xx) instead of a page stuck on Loading…; a later read that gets through clears it.
  - `UserDataProvider.tsx`: in the root layout. It gives every page the plan, progress and note stores for the source (`server`, fresh `memory`, `local`); an optional `source` prop overrides it. Until `ready` the pages render (public pages are drawn on the server) but over waiting stores whose reads never answer, so nothing reads the wrong store. A new kind of data is one field in `UserStores` and one line per source. Once ready it also points the small documents at the source (`setUserDocSource`), again whenever the source or the account changes; a forced `source` leaves them alone. It also mounts `useResumeUploads` (`features/videos/uploads.ts`), so a signed-in player's queued video takes upload on every page load.
  - `useUserDoc.ts`: the course notes, creator key, records and about me (`UserDocKind`), each one module-level copy per page. `userDoc(kind)` gives `get`, `set`, `update`, `subscribe` and `loaded`; `useUserDoc(kind)` is `[value, set, loaded]` over `useSyncExternalStore`, the empty document (`parseDoc(kind, null)`) in the server render and until it loads. The first subscriber starts the load from the source: `server` is a GET then a `DocClient` per kind, `local` the old localStorage keys (`localDocs.ts`), `memory` keeps nothing. A `set` before the load wins over it and is saved; an `update` before the load is applied over the loaded document and then saved. While it waits it reports "saving" to `registry.ts` (so the leave warning covers it); a refused load saves nothing, stays not loaded, and reports "signedOut" (401) or "rejected" (another 4xx), changes waiting or not, so the save notice tells the player (only a waiting change sets off the leave warning). A new source key (the source, plus the account id for the server) empties every document and loads again, and a late answer from the old source is dropped. Readers: `useLevel` and the singing pages (`about`), the improv roulette, the note game and the lip roll (`records`), `useCourseNotes` (`course_notes`, the index layout stays in localStorage) and `CreatorKeyProvider` (`creator`).
  - `localDocs.ts`: the `local` source: each document read from and written to the keys used before accounts (`musickit.course.notes.v2` with the move from the old key, `musickit.creator.key`, `musickit.improv.stats`, `musickit.noteGame.best`, `musickit.lipRoll.accuracy`, `musickit.level`, `musickit.level.page`, `singing.range`), with other tabs' changes heard through the storage event.
  - `SaveNotice.tsx`: mounted once in the root layout (`src/app/layout.tsx`), so pages without `PageShell` (the video studio) have it too. It shows on `failed` (the app is retrying), `stale` (changed somewhere else; the page is reloading), `rejected` (too big, or reload the page) and `signedOut` (with a **Log in** link back to the page), and while a change is unsaved (`useUnsaved`: a refused load alone holds none) it warns before the page is left.
