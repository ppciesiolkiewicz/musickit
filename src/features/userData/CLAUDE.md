# User data: rules

- **A document is parsed before it is stored and after it is read.** Both go through `parseDoc`; a stored document is never trusted as it is. A new kind is one entry in `DOC_KINDS` and one case in `parseDoc`, using the owning feature's parser.
- **`model.ts` stays client-safe.** No `window`, no `"use client"` import, no SQL. Parsers it uses live in model files, not components.
- **`server/data.ts` stays pure.** No `Request`, no SQL: it takes the repo. A new rule gets a test in `server/data.test.ts` over `repo.memory.ts`.
- **A new query is a method on `UserDataRepo`**, written in both `repo.drizzle.ts` and `repo.memory.ts`. Upserts go on the unique pairs (user, kind) and (user, exercise).
- **Size is measured as `JSON.stringify(raw).length`** against `maxDocBytes(kind)` (2 MB for the plan, 512 KB for the rest). The plan never reaches its cap by growing: `fitPlanState` drops its oldest earlier plans (then, with none left, its oldest given plans, never the newest one), in `parseDoc` and in the browser before a save, with the same cap, so the browser never sends what the server would refuse.
- **`server/` is server only.** Nothing in `ui/` or any client file imports from it.
- **A share shows only its owner's videos.** A share naming a recording that isn't one of the sharer's uploaded videos is refused (`video-not-uploaded`), so a reader never meets "This video is gone" for a take that was still uploading, and `canWatch` also checks the share's owner is the video's owner, so naming someone else's video id in a note never opens it. A visitor (null viewer) only gets the live note-share path.
- **The user id comes from the session** (`requestAccount`), never from the request. A request that changes data also sends `X-Account-Id` (`client/accountHeader.ts`), and `signedIn` refuses one naming another account with 409 `account-changed`; a new writing client sends it too.
- **Saving goes through `withRetry`.** A new kind of sender builds on it (or on `createDocClient`), so the notice, the leave warning and the `pagehide` flush cover it. Only network errors and 5xx are retried, and only those are `failed`; any other 4xx is `rejected`, so the notice never promises a retry that won't come. A sender reports through `registry.ts`; tests drive it with a fake `schedule`. The one exception is the video upload queue (`features/videos/uploads.ts`): it reports only "saving" (for the leave warning) and shows a failed upload in its own list with **Try again**, since its retry is the player's.
- **The course notes, creator key, records and about me go through `userDoc`/`useUserDoc`** (`client/useUserDoc.ts`), never `localStorage` or a module of their own. `records` and `about` are shared by several components: change a part with `update((cur) => ({ ...cur, part }))`, never `set` built from a snapshot, so a change made before the load keeps the rest of the stored document. A load never saves by itself; only a player's change does. A change waiting on the load reports its status to `registry.ts` (`saving`, then `signedOut` or `rejected` if the load is refused), so it is never lost without the save notice saying so.
- **Hashed blocks are insert-only for content and tags.** `addBlocks` never changes a stored block's content or tags and never deletes a `blocks` row. Provenance (`model`, `prompt_version`, `docs_agents`, `docs_teaching`) is the one thing filled later, once: only where all four columns are null (a block with any set is left), from the block's own `provenance`, else from its stored parent. The default slot (`minutes`, `why`, `learn_before`, `explore_more`; `NewBlock.slot`) is filled the same way, once, only while `minutes` is null, and never enters the block id. `setPlanBlocks(planId, rows)` replaces a plan's `practice_plan_blocks` rows in one transaction; account deletion removes only `block_owners` rows. A `parent_id` is written only for a block the saver owns, or saves in the same document.
- **Curated blocks are the seed file's.** `upsertCurated` (from `seedBlocks`, `db:seed-blocks`) overwrites a curated block's content, tags, slot and provenance under its fixed id; its level, steps and moves live on its `choices`, never on the block. A choice is never deleted: one no longer in the seed is set inactive, so progress and plan rows naming it keep a row.
- **A document save names the version it was loaded at.** A store that makes its `DocClient` before the load calls `setVersion` when the load arrives, and passes `onStale: reloadSoon`. `writeDoc(..., expect)` refuses a stale save (`stale`, with the stored version) before any side effect; without `expect` it always writes.
- **The teacher's comment (`StoredPlan.teacher.comment`) never reaches the owner's browser.** The owner's document GET goes through `readOwnDocVersioned`. The owner's PUT calls `writeDoc(..., { owner: true })`: the stored teacher records win (`storedTeacherRecords`), so the owner can't change, add or drop a comment or a record. A server writer (the teacher's `makeWeek`) passes no `owner`: a comment it carries wins, a missing one is put back (`keepTeacherComments`).
- **A side effect of a save never fails the save.** `writeDoc` runs `storePlanBlocks` after `putDoc`, in its own `try/catch`, and logs the error with context; it is idempotent, so the next save repairs what was missed.
