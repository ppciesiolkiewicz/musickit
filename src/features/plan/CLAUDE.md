# Practice plan: rules

What it is and where things live: `README.md`. Keep it up to date with every change.

- **Data goes through `PlanStore`** (`store/PlanStore.ts`). Components use `usePlan()` (or `usePlanStore()` for a reader outside it, like `PracticeReminder`), never `localStorage` or a store module directly: `UserDataProvider` picks the store (server, memory or local). Nothing reads `musickit.plan.backup`; no backup is kept.
- **Pure logic in `model/`** with tests (`model/plan.test.ts`): the prompt, parsing a pasted plan, links, tools, the schedule. No React there.
- Links in a plan must be attunr paths from `model/catalogue.ts`; unknown ones are dropped on paste.
- Exercise components live in `src/features/exercises` (see its README and CLAUDE.md). Their docs come from each `*.props.ts` via `npm run docs:exercises`; the plan only parses them in `model/tools.ts` (the single source for cells, the choice, tags and link resources; the prompt's interface is generated from `COMPONENT_DOCS`, never hand-listed). Nothing old is read (no migration of tool names or shapes). Nothing embedded may write the address bar.
- **Share plan** shares the stored plan the page names by id (today's own plan on `/plan`, the given plan on its page; the server refuses any other id), so it flushes the store first (`PlanStore.flush`) and refuses while the latest change hasn't landed. The invite page claims (the copy goes to `PlanState.given`, never `current`), then loads the copy's page, `/plan/given/<planId>`, with a full page load (`window.location.replace`), never a client navigation: the plan store is per session and keeps the document it read. A plan's live invites are never drawn as links in the popover (opening one claims it).
- **A given plan lives at `/plan/given/<id>`** (`GivenPlan.tsx`): every change to it goes through `updateGiven`, never `current`; it has no control that makes it the player's own. Every reader that counts a player's plans for progress uses `storedPlans` (given ones included), as the server's `playerProgress` does. On the screen a given plan is a "Shared plan", in the list ("Plans shared with you"), the page heading and the not-found state; a teacher's week is the student's "Practice plan" (the page heading, `givenPageTitle`), named "Week of 16 November" (`weekTitle`), with no Share plan. A heading or intro that depends on the reader or the plan is drawn in the browser (`PlanIntro`, `GivenPlanTitle`) and holds its space hidden until it knows, never showing the wrong words first.
- The flow modal never closes except with its Close button, and its progress survives a reload.
- **Today's plan is the server's** (`useTodayPlan`, `store/composeClient.ts`): it is asked for once per page view and date, after `PlanStore.flush`; the date follows the clock (`useClockDate`, one source for the whole page) and moves only when no edit is open and no request is out; and stored with `startDay` / `anotherDay` (both safe to call twice). The page never shows yesterday's plan as today's, never an empty plan without a line saying why, and words its states by the route's `code`, never by its `error` text. `no-blocks` is never retried by itself. A given plan is never composed over, and never drawn on `/plan` (only listed, a link to its page), except a teacher's week for a teacher's student (below). The decisions (what the page shows, what an answer does) are pure, in `model/today.ts`; the loading line shows only while a request is out. A rating is never lost to another try (`anotherDay` keeps every rated exercise).
- **A teacher's student (`Account.taught`, read with `useAccount()`) gets their teacher's weeks, never a composed day.** `/plan` draws `taughtView` (`model/today.ts`, tested) through `TaughtPlanView` and the same live view `/plan/given/<id>` uses (`LiveGivenPlan`, changes through `updateGiven`); `useTodayPlan` is `off` for them and until the account is known (no request, no Get another plan, no Change my answers, no flow modal), and the compose route refuses them (409 `taught`). "Plans shared with you" (listed for them too, under their weeks) leaves teacher weeks out; the reminder takes `taught` from the account as well (`PracticeReminder` passes it to `reminderDue`); their earlier weeks come from one order (`newestWeekFirst`, `teacherWeeks` in `model/schedule.ts`), a replaced one (in the history) listed without a link. The teacher's comment never reaches the browser: the server strips it from the document's GET, and an owner's save keeps the stored teacher records (`writeDoc(..., { owner: true })`, `features/userData/server/data.ts`).
- Flow copy follows the teaching-voice skill's "Words about the app": name who acts in each sentence, never a bare "it". Players have no outside-AI route to a plan (no prompt to copy, no AI extension writing it): flow copy never asks them to run an AI.
- **The block editor (`ui/editor/`) changes a block only through `editBlock`** (`model/editBlock.ts`, pure, tested): cells are addressed by path, every cell has an `id` (`withIds`). It receives a `Block` and callbacks, never `ExerciseMeta`; a host gives a tool cell its controls (`toolControls`), the editor imports nothing of the studio.
- **A block id is computed, never trusted** (`withBlockIds`, `model/blockId.ts`): content and tags only, cell ids left out; minutes, why and links are the slot's. It is made of the exercise as it is stored, after `cleanExercise` (`startDay`, `anotherDay`, `editDay` and `sanitiseState` alike), so a save and reload never changes it.
- **The composer's architecture is drawn on `/dev/compose` → Architecture** (`src/features/devtools/compose/Architecture.tsx`, by hand): a change to who calls `composeDay`, to `ComposeInput`, or to the calls inside it changes that view in the same commit.
- Every change: `tsx --test src/features/plan/model/*.test.ts`, `tsc --noEmit`, eslint on the feature.
