# Students

A teacher adds a student by name, email and the answers to the first questionnaire. That makes a normal account for the
student (role student, on the `taught` plan, so no setup), a `teacher_students` link, and a plan document that holds the
answers. The student signs in the first time with a claim link, mailed by the teacher's route.

## Parts

- `server/students.ts`: the rules. `addStudent` (checks in a fixed order: role, name, email, answers, plan limit, an email that already has an account; a step that fails after the account is made deletes the account again), `listStudents` (newest first, with the plan's limit), `newClaimLink` (the teacher's own unclaimed student, one a minute), `peekClaim` and `openClaim` (the claim token is used once, signs in, records `claimedAt`, goes to `/welcome`), `CLAIM_TTL` (30 days).
- `server/plans.ts`: a teacher's student's weeks. `studentView` (the student's row, the current week the teacher made, `teacherWeekOn(today)` else the newest started, with the teacher's comment, and a slider per topic of the student's areas: `now`, the `outcome()` score today, 0 when nothing is known; `atStart`, the score the day before that week started, null with no week). `makeWeek` (the link checked first; then from the document read with its version: the moved sliders recorded with `setScores` against `now` (topics of the student's areas, finite, clamped 0..3; a value sent unchanged records nothing), the comment (trimmed, at most 2000 characters, empty changes nothing) on the current week, never the new one, the start (rotate: the running week's start, replacing it; next: the upcoming week's start, replacing it, so there is at most one upcoming week (dropped when untouched, else to the history), else the day after the running week's last day; no running week: today), seven days composed (`composeStudentWeek`, seed `studentId:start:madeAt`, paced as of today at the earliest, the last day of the week before barred on day one) and put first in `given` (`giveWeek`), fitted to the cap (`fitPlanState`; still too big: `too-big`, nothing written), written with the version read; the answer's `comment` is `stored`, `none` or `no-week`; a stale write starts again from a fresh read, three tries, then `busy`; `no-answers` and `no-blocks` write nothing at all).
- `server/mail.ts`: `claimEmail` and `claimUrl` (`/claim?token=`). Sent with `sendMail` from `features/account/server/mail.ts`.
- `server/http.ts`: the routes as functions over explicit deps (`StudentsHttpDeps`) and a `Request`; `server/deps.ts` builds the real ones; the `route.ts` files under `src/app/api/students` and `src/app/api/auth/claim` only call them. Every error body is `{ error, code }`. `POST /api/students` adds, makes the first week, mails the link, and keeps the student whatever happens after the add (`plan`: made, short, none; `mail`: sent, off, failed). A student id that is not a uuid is a 404 before any query. `today` is checked with `isNearToday` from `plan/server/composeToday.ts`.
- `model/types.ts`: the shapes the routes send (`StudentRow`, `StudentList`, `AddedStudent`), shared by `server/` and the page, so no client file imports `server/`.
- `client.ts`: the page's calls, `fetchStudents`, `postStudent`, `postClaimLink`. None throws; each answers `{ ok: false, code, error }` with the route's own code and words, or the page's (`offline`, `failed`, `logged-out`, `account-changed`, `CLIENT_WORDS`). 20 s timeout, `accountHeaders`.
- The page, `/students` (`src/app/students/page.tsx`, `ui/StudentsApp.tsx`): `StudentsView` draws every state from props (who is looking, the list loading / failed with Try again / empty / listed, the limit as "n of m students" with Add a student disabled and a link to `/account` when full, the line after an add, in the warning tone when the plan or the email didn't go as meant (`addedLook`), each row's Send the link again). A row: the name, a link to `/students/<id>`; the email; "Not opened yet" or the date the link was first opened; Send the link again until it is opened. With no account (accounts off, or signed out) or an account that can't have students, a line says why, never a blank page.
- `ui/AddStudent.tsx`: adding, one step modal. Name and email first (both checked before Next), then the player's questionnaire worded for a student (`questionSteps(…, { forStudent: true })`), then a screen saying what Add student does. `today` is the device's date (`localDate()`). A failed add keeps everything typed: `name`, `email` and `exists` go back to the first screen with the line under the field, any other error shows on the last screen (`afterAdd` in `model/addFlow.ts`, pure and tested); any edit clears the line; it closes only with Close or after the add (`addedLine`: what happened to the plan, `made` / `short` / `none`, and the email, `sent` / `off` / `failed`). The flow survives a reload (sessionStorage, `ADD_KEY`).
- `ui/TeacherOnly.tsx`: the nav's Students link (`SiteNav`) shows only for a signed-in account with `can("students")`.
- The limit is the teacher's own plan row: `students` null is no limit; no plan row, or 0, is no places.
- Tests: `server/*.test.ts` over `memoryRepo` and `memoryUserDataRepo`; `plans.test.ts` with the plan feature's `stubLibrary`; `client.test.ts` over a fake `fetch`; `model/addFlow.test.ts`; `ui/StudentsApp.test.tsx` draws the page's states with `renderToStaticMarkup`.
